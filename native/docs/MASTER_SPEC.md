Owner's single master specification (received 31 Oct 2026). It incorporates all earlier requirements, reported bugs, feature-ownership decisions, Accounting and Company mockup instructions, employment, financial and design rules. Do not treat earlier prompts as separate projects. SIMULATION_RULES.md and DESIGN_RULES.md remain binding and are compatible with this document; where this document is newer and conflicts with an earlier design decision, this document wins and the conflict is recorded in `master_audit/CONFLICTS.md`.

Repository branch: native-swiftui (native SwiftUI).

## 1. Objective
Improve the existing Ledger game into a coherent, realistic, professional business-management simulation: managing businesses, employees, companies, chains, investments and finances as if running real businesses. Every feature must: have one clear place; connect to the correct underlying system; have meaningful gameplay consequences; display information the player could reasonably know; work with the rest of the game; preserve existing saves and working features. No collection of disconnected screens, duplicated systems or unfinished buttons.
Rewriting is allowed only to solve an identified problem. For every substantial change understand: what is wrong; why; which systems depend on it; the correct behaviour; what must NOT happen; how it connects to the rest. Do not blindly follow old audit findings: verify against the current repository.

## 2. Critical working rules
A. PRESERVE WORKING CODE: do not rebuild the app; do not regenerate large files unnecessarily; do not replace functioning systems for cleanliness; smallest complete change; preserve rules, data, saves; reuse models/services/calculations/components; avoid rereading the whole repo; retain audit findings once a file/system is audited.
B. NO UNAPPROVED FEATURE REMOVAL: you may investigate/question/recommend removing or merging. You MUST obtain explicit approval before: permanently deleting a feature; removing significant functionality; removing an established system others depend on; major or risky architectural change; any change that could destroy save data. For each recommendation explain: what it does; duplicated/unnecessary?; dependent files/systems; what is preserved; the replacement; risks and alternatives. UPKEEP is under review: investigate whether it adds gameplay or duplicates other systems; recommend retain/merge/remove; do not delete without approval. Silence is not approval.
C. WORK IN STAGES (Section 5). Complete a coherent stage, integrate, report, proceed. Group related work; no hundreds of tiny tasks.
D. NO DUPLICATE SYSTEMS: one authoritative system per shared data type, calculation and rule; other screens show summaries or link to the canonical destination; do not fix a broken screen by creating another implementation.
E. SAVE COMPATIBILITY: if a migration is needed explain why, identify data, preserve information, test through GitHub CI, never silently reset or discard saves.
F. NO FAKE FUNCTIONALITY: no buttons that do nothing; no decorative documents that are not real game records; no notifications without events; no meetings without decisions; no empty menus; no fake integrations; no fake financial information; no placeholders presented as complete. If a feature cannot yet be done properly, explain the limitation.

## 3. Parallel agents
Use parallel agents where safe, organised around connected systems, not random screens.
A. NEVER split connected systems between competing agents. Do NOT assign Banking, Company Finance, Accounting and Payroll to different agents: ONE financial-systems workstream owns the connection between: Bank (accounts and balances, transfers, loans and financing, actual payment execution, liquidity and debt); Accounting (transaction records, bookkeeping and categorisation, payroll administration, invoices and reconciliation, suppliers and supplier records, documents and tax records, permissions); Company (operational financial summaries, employee contracts and staffing costs, products, equipment, inventory, premises, operations); Group (ownership, company equity, holdings, group-level financial information). All use the same underlying financial data and payment engine.
B. Allowed parallel work when genuinely independent: navigation and routing audit, employee avatar alignment, startup product form, board meeting workflow, main menu layout, public-release file classification (still check shared-file dependencies).
C. Ownership rules: map files and dependencies; define each agent's responsibility; files each may edit; files with only one owner; interfaces/data contracts; one integration owner. Agents must not independently redesign the same model, navigation system, financial calculation or shared component; never edit the same files simultaneously; no competing versions of a feature.
D. INTEGRATION OWNER (the main agent): architecture, conflicts, review, integration, checking connections, preventing duplicates, save compatibility, no requirement silently forgotten. An agent finishing its files does NOT mean the feature is complete: complete only when connections to the rest of the game work.
E. BRANCH MANAGEMENT: keep GitHub branches to an absolute minimum. Prefer working on native-swiftui. No branch per agent/bug/feature. Separate branches only for genuine isolation/conflict prevention/rollback. Focused commits; no history rewriting or resets without reason; inspect the working tree first; never overwrite another agent's uncommitted work.

## 4. Testing and GitHub CI
Normal testing happens through GitHub CI (existing workflows). No excessive local test runs after tiny changes.
A. Inspect existing workflows; use code inspection, reasoning and existing checks for small tasks; accumulate related changes into coherent integration points; run CI after meaningful stage integrations and major merges; extra CI runs for critical financial calculations, navigation architecture, save compatibility or other high-risk behaviour.
B. Do not trigger a full build/test per tiny fix; group fixes; use focused inspection, relevant existing tests, CI at integration points, broader regression at the end of major stages.
C. Local testing only when CI cannot reproduce/diagnose, a check is unavailable in CI, a failure needs local reproduction, or a tool is required before safe integration; say why.
D. CI discipline: no identical CI runs repeated needlessly; do not change CI merely to hide failures; do not disable tests for green; no success claim until GitHub reports the workflow passed; distinguish build success from gameplay verification; state what CI cannot test.
E. Broader CI after: navigation integrated; financial systems integrated; employment and payroll integrated; startup and investment integrated; major UI and data-flow changes; final regression and release preparation.

STAGE 2 — FINANCIAL SYSTEMS, BANKING, ACCOUNTING AND COMPANY CONVERSION (ONE connected workstream, one owner).
A. BANKING APP (Banking mockup): own visual identity: dark forest-green/charcoal headers, warm ivory content surfaces, restrained champagne/gold, refined financial typography, professional private-banking look. Bank owns: personal accounts and finances; company bank accounts and balances; transfers; loans and loan applications; financing and credit decisions; interest rates and debt; deposits and withdrawals; liquidity; actual execution of payments. Bookkeeping does not move into Bank.
B. ACCOUNTING APP: dedicated Accounting & Compliance app inside Phone, Accounting mockup authoritative for visuals and navigation (dark forest-green/charcoal header, ivory/cream surfaces, champagne/gold accents, compact rows and subtle separators, professional accounting-software look, same screen organisation and hierarchy; not a generic dashboard or oversized cards). Accounting owns: company transaction ledger and categorisation; income and expense records; payroll administration and payslips; employee hours and timesheets; customer and supplier invoices; payment tracking and reconciliation; supplier records and agreements; accounting documents and company records; tax and accounting filings; accounting access and permissions; accounting settings and supported integrations.
 Home: business selector; Transactions; Payroll; Invoices & Payments; Suppliers; Documents; Settings.
 Transactions: All/Income/Expenses; date range; search; list; details; categorisation and notes where permitted; links to associated records.
 Payroll: Overview; Employees; Timesheets; Run payroll. Run payroll shows employees included; gross wages; employer taxes and contributions; deductions where supported; total employer cost; account to be charged; available balance; review before payment; execute through the existing Bank payment engine; generate payslips; update transaction records; prevent duplicate payroll for the same period.
 Invoices & Payments: Invoices and Payments; Draft/Sent/Paid/Overdue; customer and invoice details; line items, tax and payment status; actual payment recording; correct company account and ledger updates.
 Suppliers: one canonical destination; search and list; add supplier; profile; agreements, terms, purchases, invoices, deliveries; inventory links and transaction history. Adding a supplier must not automatically purchase anything.
 Documents: Company / Tax / Contracts: registration documents; legal form; ownership records; licences and permits; tax filings; VAT records where supported; supplier, customer and employment contracts; financing documents; chain and franchise applications and agreements.
 Settings: access management; accountant and manager permissions; company-specific access; integrations supported by the game; accounting settings.
 Access rules: Owner full; Accountant appropriate accounting and payroll; Manager limited by authority; other employees no automatic confidential access. Access to one company must not grant access to every company in the group.
C. FINANCIAL CONNECTION RULES: Accounting manages and records; Bank holds money and executes payments. Running payroll in Accounting must: calculate using the authoritative employment and payroll data; select the correct company account; validate funds; execute payment through Bank; record the transaction in Accounting; generate payslips; update Company, Team and Reports. No duplicate balances, transaction engines, payment systems or payroll calculations. Company shows financial summaries; detailed bookkeeping belongs in Accounting.
D. COMPANY CONVERSION TO A LIMITED COMPANY: currently does not work correctly. Reproduce and trace the whole process. Check: legal form; company identity; ownership; assets and liabilities; accounts; employees; contracts; taxes; documents; save data; Bank and Accounting connections; Group ownership; reports. Do not simply change the displayed label. Conversion must update the legal and financial structure throughout. Show requirements, costs, consequences, ownership changes, account to be charged. Ask whether the cost is paid from the private/personal account or the company/business account; show balances; validate affordability; record the payment correctly; preserve history and records. Test conversion, cancellation, insufficient funds, save/load and subsequent simulation days.
E. COMPANY VALUE AND PERSONAL NET WORTH: show the player's attributable company equity in the personal wealth overview using actual ownership; include relevant debt where supported; distinguish estimated private-company value from cash and liquid assets; never count company value twice; never present estimated valuation as money available to spend.
F. LOANS: two stages: 1 initial application; 2 bank assessment; 3 display maximum approved amount; 4 show interest, period, conditions, instalments; 5 player chooses how much to borrow; 6 final agreement; 7 confirm and pay into the correct account. The player must not be forced to borrow the maximum. Fix early repayment: correct principal, future interest, schedule, invoice status, invoice month, no duplicate invoices, save/load.
G. FINANCIAL REALISM: equipment purchase is a cash outflow when paid; depreciation reduces accounting profit and book value, not cash again; loan principal and interest separate; prevent inventory and supplier costs counted twice; reconcile cash, profit, assets, liabilities, payroll, taxes, debt; believable cost structures per business type; a solo home-based business must not inherit the overhead of a staffed physical shop.
H. COMPANY OVERVIEW AND STATS: cash is the primary financial figure, profit secondary; normal Company Overview fits one screen on supported phones; do not duplicate cash in Stats/Information; use actual financial data for expense breakdowns; include margin, ownership, legal and company information; preserve statements and records. Evaluate the Company Finance tab name (Stats, Information or Documents) by actual content.
DONE WHEN Bank, Accounting, Company and Group show consistent financial information from one authoritative financial system.

STAGE 3 — EMPLOYMENT, HIRING, TEAM AND PAYROLL INTEGRATION (connected to Stage 2). Payroll administration stays in Accounting, payment execution in Bank, employee contracts and management in Company → Team. No separate payroll or employee systems.
A. EMPLOYMENT TYPES: hourly, part-time, seasonal, temporary, full-time, fixed monthly salary. Working percentages include 20%, 50%, 80%, 100%. Percentage affects contracted hours, expected and actual hours, gross wages, employer contributions, insurance and benefits, payroll, cash, operational capacity and productivity. Seasonal and temporary employment have meaningful dates and consequences. Do not force every hire into permanent full-time.
B. EMPLOYER COST shown separately: gross hourly wage; working percentage; expected hours; gross annual wages; employer taxes and contributions; insurance; benefits; other employment costs; total monthly employer cost; total annual employer cost. Use the country rules the game supports; no invented universal rates. Same authoritative calculation in hiring, employee profiles, Team, payroll, company forecasts, accounting records.
C. TWO-PAGE HIRING NEGOTIATION. PAGE 1 CONTRACT TERMS: contract type; working percentage; seasonal/temporary duration; benefits; company vehicle or own-car arrangement; other conditions; promises; career and responsibility expectations; then Next. Own car has no unrelated tab of its own. PAGE 2 SALARY NEGOTIATION: distinguish Your offer, Their asking amount, Market pay. The market option is labelled "Offer market pay". Show the actual hourly wage and total annual employer cost. "Offer what they ask" appears only after the candidate has actually made an asking offer or counteroffer. All displayed amounts and applied contract values match. Negotiation considers: candidate expectations; role; market; company finances and size; company development stage; experience and qualifications; the full contract package. Small businesses may attract candidates who value responsibility or opportunity, but not everyone accepts low pay.
D. EMPLOYEE PROMISES: salary review; promotion; additional responsibility; training; better conditions; future benefits; agreed working percentage changes. Recorded under Company → Team → Promises: employee; promise; date made; due date; status Pending/Due/Fulfilled/Broken/Renegotiated; consequences. Only promises connected to real game systems.
E. AFTER-HIRING CHANGES: working percentage; hourly wage; fixed salary; contract type; seasonal duration; benefits; responsibilities; position. Before confirmation show current employer cost; new employer cost; monthly and annual difference; hours difference; payroll impact; operational impact. The employee does not automatically accept every significant change. Preserve contract history.
F. REALISTIC EMPLOYEE BEHAVIOUR: remove unrealistic exact predictions such as "chance of staying"; do not expose hidden probabilities or personality numbers. Employees negotiate, express dissatisfaction, disengage, give notice, leave unexpectedly, communicate professionally, handle disagreements poorly, stop communicating in appropriate circumstances. No crude age stereotypes.
G. HIDDEN SKILLS AND PERFORMANCE FEEDBACK: never display internal values such as Skill 25, Boldness 46, Trust 72. Use observations: work quality, reliability, speed, mistakes, initiative, communication, independence, completed tasks (e.g. "Completed most assigned work, but needed regular guidance."). Feedback comes from actual simulated events, not a numerical rating translated into a sentence.
H. TEAM AND PAYROLL RESPONSIBILITY: Company → Team shows compact metrics: workers; average hourly rate; total hours; total payroll cost. No large payroll-run workflow in Team. Responsibility: qualified accountant automatically; else suitable manager without extra fee; else the player. Do not automatically hire an accountant. Tie to actual qualifications, permissions and authority.
I. AVATARS: fix employee icon/profile image alignment in the shared component; check lists, candidates, employee details, Team and Group.
DONE WHEN the complete employment lifecycle works: negotiation, payroll, contract changes, departure.

STAGE 4 — STARTUP, INVESTMENT AND BUSINESS CREATION.
A. STARTUP LIFECYCLE: audit product development, launch, sales, customers, revenue, costs, hiring, expansion, investment, exit. A product at 100% leads into a meaningful launch and commercial phase. Connect product quality, pricing, marketing, demand, customers, capacity, revenue, operating costs. Hiring and firing affect development, capacity, payroll, operations.
B. INVESTMENT: keep distinct: 1 new share issuance to raise company capital; 2 existing shareholder selling shares; 3 founder selling a stake; 4 full acquisition or exit. Show valuation; share price; ownership before/after; shares issued or sold; dilution; company proceeds; personal proceeds; conditions. Correct repeated rounds and share calculations.
C. PRODUCT EXPANSION: a real native SwiftUI form with only gameplay-relevant fields; costs, requirements, timeline, expected effects, remaining cash; cancellation changes nothing; save/load preserves the decision.
D. BUSINESS CREATION AND ACQUISITIONS: separate founding a business, acquiring an existing business, acquiring a football club. Show mandatory costs, optional stock/equipment, deposits, fees, working capital. Never silently buy optional stock or equipment. Show remaining cash before confirmation. Offer realistic alternatives when affordable. No unavoidable immediate bankruptcy through automatic hiring or purchases. Audit automatic spending across every business type.
DONE WHEN startups operate, earn, expand, raise capital and exit; business creation is financially transparent.

STAGE 5 — COMPANY OPERATIONS, MARKET, PRICING, SUPPLIERS.
A. COMPANY MOCKUP: follow closely for layout, navigation, section order, hierarchy, compact rows, spacing, overview structure, contextual links. The Company app retains Ledger's ORIGINAL Company colours; do not apply the Banking colour scheme to Company.
B. OWNERSHIP: Company owns operations, products and services, employees and management, premises, equipment, inventory, pricing, marketing, operational decisions, performance summaries. Accounting owns bookkeeping, payroll administration, invoices, suppliers, documents, tax records. Bank owns accounts, financing, payment execution.
C. PREMISES AND UPKEEP: investigate "Where you work", "Premises" and "How you sell"; if they manage the same locations, recommend merging into one destination preserving distinct functions. Investigate Upkeep and other maintenance systems for duplication. Do not delete anything without approval.
D. SHARED MARKET APP: one shared Phone app; select the business analysed; contextual company links open Market with the right company selected; preserve business-specific market data and simulation effects.
E. PRICING: one canonical pricing editor and authoritative pricing source; other screens link to it with the business/product selected. Preserve distinct concepts such as base price, promotions, contract prices. Price setting must not be counted in stages -1 -2 -3 +1 +2: the player sets manual prices, e.g. "price per hour (after tax, what the company gets per hour)", and if a company sells more than one product or service sets individual prices, unless it is a store selling many different things, then the player sets a percentage on all items on top of the items' cost. Changes persist and affect the simulation.
F. SUPPLIERS: Accounting is the canonical supplier-record and agreement destination; Company Operations remains responsible for operational purchasing, equipment and inventory decisions. Purchases connect to supplier records, inventory, transactions and Bank payments. No separate supplier databases.
G. CHAINS AND FRANCHISES: applications accessible in the appropriate Company context and recorded in Accounting → Documents → Contracts. Process: review requirements; review terms; sign documents; submit; wait for meaningful review; receive a decision. No instant approval. Realistic financial, contractual and operational requirements, not arbitrary time gates.
DONE WHEN operations, Market, pricing, suppliers and chain/franchise applications share the right systems.
